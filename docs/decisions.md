# 决策记录

记录本项目的重大技术决策（选型、数据模型、外部服务）。每条：日期、决策、为什么、放弃了什么。

## 2026-10-14 技术栈与构建管线（票1 / #2）

| 日期 | 决策 | 为什么 | 放弃了什么 |
|------|------|--------|------------|
| 2026-10-14 | 外壳用 Tauri 2 + Rust（系统 WebView2） | 安装包体积优先：本骨架安装包仅 1.88 MiB；WebView2 在 Win10/11 自带 | Electron（安装包 80 MB+、内存占用高） |
| 2026-10-14 | v1 只做 Windows | 实际运行环境是 Windows 宿主；壳本身跨平台，其他系统以后需要再说 | 同时支持 Linux/macOS（构建与验证矩阵翻倍） |
| 2026-10-14 | 构建管线：WSL2 + cargo-xwin 交叉编译 + NSIS，一条命令出安装包 | 开发在 WSL2；实测增量后 3m42s 直接产出 Windows 安装包，不需要第二套环境或 CI 往返 | GitHub Actions 构建（要推代码、等 CI）；Windows 侧装完整 Rust 工具链（几 GB、需管理员） |
| 2026-10-14 | 前端 Vite 8 + TypeScript 7，不用 UI 框架 | 配置界面规模小，去掉框架依赖可减小包体与构建复杂度 | React/Vue |
| 2026-10-14 | 纯逻辑独立成 crates/dsharbor-core 库 | 开发机 WSL2 没有图形环境，逻辑独立后核心部分可全自动 `cargo test`；外壳层在 Windows 手动验收 | 逻辑直接写在 Tauri 应用里（测试必须依赖 GUI/Windows 环境） |
| 2026-10-14 | 静态检查按 Windows 目标跑（cargo-xwin clippy） | v1 交付的就是 Windows 二进制，在真实目标平台上过 clippy 更有意义 | 在 WSL 装全套 GTK/WebKit 开发库以便主机 clippy（对本项目交付无价值） |

## 2026-10-14 登录链接的获取通道（票3 / #4）

| 日期 | 决策 | 为什么 | 放弃了什么 |
|------|------|--------|------------|
| 2026-10-14 | 首选桥接插件（dsharbor-bridge），日志解析 `dsh web: <url> (LAN: …)` 作兜底 | 官方已明确 token 只能进程内生成、禁止外部指定；日志格式无稳定性承诺，而插件经内部 `connection.authenticatedUrl()` 现场铸造链接是与官方机制同源的稳定路径 | 只靠 stdout 解析（上游改输出格式即失效）；要求固定 token 的第三方插件（官方否决方向） |
| 2026-10-14 | 插件接口用一次性 nonce 鉴权：壳每次启动生成 128-bit hex，经环境变量 `DSHARBOR_BRIDGE_NONCE` 注入，插件接口 `GET /dsharbor-bridge/url?nonce=…` 恒定时间校验 | 用户 webserver 绑定可能不是回环（本机实际是 0.0.0.0），接口在局域网可达；nonce 只驻内存、不落盘，缺 nonce 时接口只回 503，用户直接 `dsh web` 完全不受影响 | 接口无鉴权（局域网可被任意进程/机器取走带 token 的链接） |
| 2026-10-14 | 安装/卸载走官方 `dsh plugin --profile web add\|remove file:<tgz>`，壳侧操作前自动备份 profile 文件 | 官方 plugin-manager 会按包的 `dsh.bundle` 声明自动登记/摘除 `dsh.profile.bundles`，不手改用户配置；备份提供一键回滚 | 手改 `cordis.patch.yml` 注入（会碰「托管，勿改」块、破坏用户配置的升级路径） |
| 2026-10-14 | 壳内取链接的 HTTP 客户端手写（TcpStream + Content-Length/chunked） | 只需一个本地 GET；避免引入 reqwest/ureq 的传输栈与证书包；能用本地 stub 服务器做全自动测试 | reqwest / ureq 等现成客户端库 |
| 2026-10-14 | 「打开 DSH 界面」命令必须是 async（不能是同步命令） | Tauri 官方文档明确：Windows 上在同步命令/事件处理器里调 `WebviewWindowBuilder::build()` 会死锁（WebView2 已知问题，tauri#13092）。实机踩到：第二个窗口白屏、页面导航永远挂起、窗口关不掉，改 async 即好 | 同步命令（代码更简单，但在 Windows 上窗口不可用） |
| 2026-10-14 | WSL 模式的 PATH 由宿主侧清洗后以 `env PATH=…` argv 注入（剔除 `/mnt/*`，补 `~/.local/share/pnpm/bin`、`~/.local/bin`） | 从 Windows 经 wsl.exe 启动发行版时，Windows 侧 PATH（含 `/mnt/d/…` 的 Windows 版 pnpm）会混进发行版，DSH 插件管理执行裸 `pnpm` 时崩在 `current dir is an absolute path with drive letter`；pnpm 自己的 PATH 配置在 `~/.bashrc`，非交互 `bash -lc` 读不到，必须显式补 | 在 inner 命令里塞 shell 清理脚本——实测 wsl.exe 会破坏参数中的引号（`echo X"Y"Z` 变 `XYZ`），含引号的脚本必被改坏；依赖登录 profile 自带 pnpm（读不到 .bashrc） |

## 2026-10-14 轻量模式（票4 / #5）

| 日期 | 决策 | 为什么 | 放弃了什么 |
|------|------|--------|------------|
| 2026-10-14 | 轻量模式状态机放核心库（`Normal/Light/Exiting` + 事件 → 副作用清单），托盘点击与关窗事件走同一个 `dispatch_lifecycle` | 「托盘状态不同步、反复关开白屏」是这类交互最容易出错的地方；状态机纯逻辑化后能用事件序列全自动测试（含 5 轮关开），副作用执行集中在一处，不存在两条路径各写一半 | 状态散在外壳的各个事件回调里（难测、容易漏路径） |
| 2026-10-14 | 关主窗口 = 拦截默认关闭并立即 `destroy` 窗口（不是隐藏/最小化）；所有窗口关闭触发的 `ExitRequested`（code 为 None）在非「完全退出」时 `prevent_exit`，应用留在托盘 | 轻量模式的目标是释放界面内存：销毁 WebView 后 WebView2 进程整棵退出（实测量级明显），隐藏/最小化则内存照占；`prevent_exit` 只在 code 为 None（窗口耗尽）时生效，托盘「完全退出」与显式退出不被拦 | 隐藏窗口（实现简单但内存不释放）；不拦退出（关窗即退壳，DSH 常驻无从谈起） |
| 2026-10-14 | 托盘图标创建失败视为启动失败（直接终止启动） | 没有托盘的轻量态意味着窗口关掉后应用再也回不来——宁可启动即报错，也不要留下一个够不回来的常驻进程 | 托盘失败时继续启动（会在「关窗后失联」时变成幽灵进程） |

## 2026-10-14 打开方式、窗口独立与托盘调整（维护者要求）

| 日期 | 决策 | 为什么 | 放弃了什么 |
|------|------|--------|------------|
| 2026-10-14 | 提供两个独立的打开方式：「当前程序打开」（壳内 WebView2 窗口）与「浏览器打开」（系统默认浏览器）；DSH 启动仍恒带 `--no-open` | 维护者要求两种方式并存——平时用壳窗口（关窗即释放内存），偶尔需要浏览器生态时手动开一次；但自动弹出浏览器仍是禁忌，所以把「浏览器」做成显式动作而非默认行为 | 只保留 WebView2 单通道（浏览器场景无入口）；依赖 DSH 默认弹浏览器（不可控、占用大） |
| 2026-10-14 | 启动界面（`main`）与 DSH 界面窗口（`dsh-view`）相互独立：关一个不连带关另一个；关主窗口只销毁主窗口（轻量语义作用于被关的那个窗口） | 维护者明确要求。此前「关主窗口连带销毁 DSH 窗口」释放内存最彻底，但不符合「窗口互相独立」的使用方式 | 沿用连带销毁（用户开着 DSH 窗口时点主窗口 X，DSH 窗口也一起消失） |

## 2026-10-14 界面细节与窗口健壮性（维护者第二轮要求）

| 日期 | 决策 | 为什么 | 放弃了什么 |
|------|------|--------|------------|
| 2026-10-14 | DSH 界面窗口（`dsh-view`）尺寸 = 主显示器逻辑尺寸的 92%/88%，上限 1280x860、下限 760x480 | 维护者实测：125% 缩放的 1536x864 屏上固定 1200x800 会高出屏幕下边界 | 固定 1200x800（越界）；记住用户手动调整的尺寸（多一份状态，Windows 本身会记窗口位置） |
| 2026-10-14 | 主窗口重建改经 `AppHandle::run_on_main_thread` 排队到主线程再 `WebviewWindowBuilder::build()` | 实测从 async_runtime 任务直接建窗会出现窗口重建不出来、壳进程随后消失（tauri#13092 家族）；票4 期从托盘事件回调（主线程）同步建窗是已验证可用路径 | 在异步线程里直接 build（会复现崩溃）；自建窗口消息泵 |
| 2026-10-14 | 托盘菜单在「重启 DSH」下新增「停止 DSH」，与界面「停止」同源（`tray_stop_dsh` → `stop_session`），只停后端、不动壳生命周期 | 维护者要求；「停止后端」与「退出壳」是两个语义，混进「完全退出」会让中间态含糊 | 复用「完全退出」（语义混淆）；让「停止」顺带退壳（用户失去托盘入口） |
| 2026-10-14 | 「最近输出 / 操作输出」统一为带旋转箭头的折叠块（默认收起、点击标题整行展开/收起），空态显示「（暂无输出）/（暂无操作）」；下拉框与滚动条统一美化 | 维护者反馈点击开关没有可感知反馈：收起时看不出可点，内容为空时展开了也像没反应 | 常开显示（占版面）；保留原生小三角（可点区域小、空态无反馈） |
| 2026-10-14 | 「最近输出」在启动 / 停止 / 重启 DSH 后自动展开；「操作输出」在桥接安装 / 卸载 / 恢复后自动展开（`expandLog()` / `expandBridgeOutput()`，在发起 invoke 前展开） | 维护者澄清（m03145）——要的不是「可点开」而是「点启动 DSH 后同一卡片的最近输出自动展开；桥接卡片点安装/卸载等有终端输出时自动展开操作输出」：终端输出就是操作结果，默认摊开省一次点击 | 只做到「可点击展开」（本轮已确认可用，但用户需要再点一次）；等输出到达再自动展开（时机复杂，反而看不到过程） |

## 2026-10-15 含空格安装路径下的插件安装（v0.1.0 实机缺陷）

| 日期 | 决策 | 为什么 | 放弃了什么 |
|------|------|--------|------------|
| 2026-10-15 | 安装桥接插件前把 tgz 暂存到无空格目录（宿主 `%APPDATA%\DSHarbor\cache`；WSL 内 `/tmp/dsharbor-bridge`），再执行 `dsh plugin add file:<暂存路径>` | v0.1.0 实机缺陷：默认安装目录 `D:\Program Files\DSHarbor` 含空格，pnpm 解析 `file:` 规格时在空格处截断、把 `file:D:\Program` 当包名去 registry 查（ERR_PNPM_PACKAGE_MANAGER_ADD_RESOLVE_LATEST / 404），安装必失败；暂存后走的是此前已实机验证过的无空格路径 | 对路径做 `file:///…%20…` URL 编码（依赖 pnpm 的 URL 处理、未实测，WSL 侧还要处理 /mnt 前缀）；要求维护者把壳装到无空格目录（安装器默认路径就含空格） |
